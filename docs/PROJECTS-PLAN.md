# Project workspace implementation plan

## Requirements and boundaries

1. Real execution contexts: pick allowed server directories and Git checkouts;
   persist a primary cwd plus explicit additional roots. Never use process.chdir.
   Runtime tools, persona, plugin tools, commands, review policies and delegated
   workers must resolve the same immutable stream context. Changing a project's
   settings affects new streams, not already-authorized active work.
2. Secret integrations: browser write-only credential submission, no transcript,
   SSE, export or localStorage secret values. Private encrypted local vault;
   explicit OpenBao KV and external password-manager providers. Server keeps
   provider trust/address/config; HTTP input cannot run arbitrary secret commands.
3. Projects: nested grouping, multiple directories/repositories/streams, per-agent
   membership, archive/soft-delete, conversion and drag/drop of sessions. Existing
   transcript store migrates additively, without destructive history changes.
4. Notifications: persisted terminal turn revisions + per-principal read markers;
   completion/failure points in collapsed project/session trees, no polling model.
5. Dashboard: project overview and aggregated activity, safe statuses, centered
   next-step composer, explicit stream target and stable task ownership.
6. Federation: expiring, single-use pairing generated by the target via WebUI or
   privileged startup-plugin command; validate over authenticated HTTPS, retain
   scoped peer tokens only in encrypted server vault. Central browser never sees
   peer tokens. Per-agent names/colors and connection states; project fan-out must
   expose partial failures and never retry unknown productive submissions blindly.
7. Network: canonical origin + exact Host checks, HTTPS, scrypt operator login,
   HttpOnly/Secure/SameSite session cookies, expiry/revocation, same-origin mutation
   checks, principal-bound project/session ownership and SSE authorization.
   No permissive CORS, trusted-forwarded-header inference or anonymous LAN mode.

## Vertical slices and acceptance

A. Generic Core execution-context capability + plugin-owned projects/pickers:
   verify two simultaneous directories, actual tools and formal review binding,
   delegated inheritance, persistence/restart and refusal to retarget a used stream.
B. Project UI: expandable tree, menus, + stream, dashboard, activity/unread,
   archive/delete/convert/move; Chromium keyboard/mobile/scroll regressions.
C. Secrets and Git providers: secure file/key handling, AEAD, origin-bound remote
   calls with redirects refused, provider adapters, no secret in API/event history.
D. Network identity: login/logout/expiry, authority mapping and per-principal
   isolation; test every HTTP/SSE route, CSRF/rebinding, TLS startup requirements.
E. Multi-agent: consume/replay/expiry tests, scoped token revocation, central SSE,
   project synchronization receipts, disconnected-agent handling and cleanup.
F. Final gates: existing plugin tests, new backend/security/Core integration,
   real Chromium scenarios, Core typecheck/full suite, normal PR/release workflow.

## Development checkpoint

- Headless packages exist separately: workspace, credentials, git-catalog and agent-hub.
  WebUI consumes versioned services; no new repository/framework is required.
- A/B: persistent contexts, real concurrent PI tool cwd, captured worker ancestry,
  actual formal review in separate Git checkouts, headless Core integration and
  Chromium project/stream/conversion/mobile flows pass local tests. Legacy chats
  now attach under Existing chats and can be converted/moved into projects without
  changing their original webui session key, transcript or execution cwd.
- C: local AEAD vault, OpenBao provider, read-only GitHub/Forgejo discovery and
  operator-owned checkout mappings are implemented. OpenBao/Git tests use injected
  transports; no live organization/vault integration has been verified. Automatic
  clone/Git-process credential injection and concrete password-manager adapters
  remain outstanding.
- D: single-operator authenticated native HTTPS is implemented in development:
  independent identity service, local hidden-password bootstrap, audience-bound
  opaque sessions, secure HttpOnly cookies, bounded scrypt login, expiry/revocation,
  exact authority/Origin checks and HTTP/SSE guards. Temporary loopback TLS and real
  Chromium login/logout tests pass; multiuser hosting is explicitly not supported.
  Existing loopback defaults and all live network configuration are unchanged.
- E: concrete headless Hayate HTTPS transport now pairs two instances, scopes work
  to explicitly mapped target projects, propagates settings and sends/reads target
  stream messages. Target-side token expiry/revocation and explicit per-agent sync
  receipts are implemented. Actual Core plugin/channel and Chromium multi-agent
  registration/send/revocation tests pass. The project dashboard now combines
  local and mapped remote streams, with explicit target selection, unread markers
  and five-second read-only refresh while visible. Remote conversations show text
  and tool activity inline; new-stream creation is idempotent and feature-checked.
  Federated SSE and non-Hayate runtime adapters remain outstanding.
- Latest overlay verification: 18 backend cases (including actual target Core),
  28 WebUI HTTP/lifecycle/TLS cases and four Chromium flows. The multi-agent
  browser flow registers a real loopback-TLS target, sends work and revokes its
  target token; disconnected revocation retains credentials for reconciliation.
- F: Core full suite (including development-materialized review adapter): 1597
  pass, one existing skip; Plugins adapters 63 pass; backend packages 12 pass;
  WebUI HTTP/lifecycle/TLS 28 pass; identity tests 2 pass; all three Chromium
  suites and workspace/identity headless host integrations pass. Overlay publication,
  released-host compatibility and operator-controlled rollout remain separate gates.
- Distribution is deliberately simple: independently installed overlay checkout,
  required base contracts/service versions checked on activation, no mandatory
  overlay revision pin or backend packaging in Core. Existing bundled Core adapter
  maintenance is a separate concern.

## Compatibility and rollout

Work occurs in isolated `project-core` / `project-webui` worktrees. Existing mixed
checkouts and live homes are untouched. UI/integration behavior stays in Plugins;
Core supplies only immutable context binding and consumers' resolution contract.
The shipped review adapter must adopt that contract; older engines must refuse
non-default contexts rather than silently reviewing the wrong checkout.

No live DNS, certificate, Secret-store permissions, org credentials, agent trust,
network listener or homelab rollout changes are made by development. Those require
explicit operator configuration and verified rollout after source integration.
Implemented features and outstanding slices must be reported separately; a plan,
mock or passing unit test is not proof of a live remote integration.
